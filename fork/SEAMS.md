# Seams — every place the fork edits an upstream file

The fork's code lives in `fork/`, `lib/fork/` and `test/fork/`. Upstream files are edited
**only** at the seams below. Each seam is wrapped in markers so `git grep -n "\[fork\]"`
finds it:

```dart
// [fork] <seam id>: <one line on why>
...fork lines...
// [/fork]
```

(Gradle and XML use their own comment syntax.)

Add the row in the same commit that adds the seam. A seam that is no longer needed (for example
because upstream merged the feature) gets removed, and so does its row.

The seam table comes last: `.gitattributes` merges this file with `merge=union`, which adds
new rows at the end of the file, so they land in that table.

## Fork-owned copies

An upstream screen the fork has mostly rewritten is not patched in place. It is copied whole
into `lib/fork/`, the fork's copy is wired in with one seam (the route, or the parent that
builds it), and the upstream file goes back to exactly what upstream has (D23). Upstream's
tests keep testing upstream's file; the fork's tests test the copy.

**On each upstream release merge**, upstream's changes to these files no longer arrive by
themselves. Run `fork/tools/upstream-copies.sh <release tag>`: for each row it prints what
upstream changed in the file since the copy was taken (`--patch` for the diff). Port what
applies to the fork's copy, then set the row's "Upstream at copy" to the release.

## Carried upstream changes

Upstream-bound work (rule 1) is built on a branch off `develop`, cherry-picked (`-x`) into a
`fork/<topic>` branch, and carried without markers until upstream merges it. When the PR lands on `develop` the fork takes
upstream's commit (the `upstream-merge` skill, "When one of the fork's PRs lands on develop") and
the row says so; the release merge then finds the files equal and the row goes.
